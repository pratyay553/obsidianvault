## Objective
Learn how to profile Java threads to find CPU hogs, lock contention, and latency bottlenecks.

---

## Beginner Explanation
Profiling means measuring what your application is actually doing — which threads consume the most CPU, which locks cause the most waiting, and where time is being spent. Tools do this for you without modifying code.

---

## Technical Deep Dive

### Key profiling questions
1. Which thread(s) are consuming the most CPU?
2. Which locks have the most contention (threads waiting)?
3. Which method calls account for most of the elapsed time?
4. Are threads blocked when they should be running?

### Profiling tools

#### Java Flight Recorder (JFR) — production safe
```bash
# Start recording
jcmd <pid> JFR.start name=profile duration=60s filename=profile.jfr

# Or at JVM start:
java -XX:StartFlightRecording=duration=60s,filename=profile.jfr MyApp

# Analyze in Java Mission Control (JMC):
jmc profile.jfr
```
JFR overhead: ~1–2%. Safe for production. Captures:
- Thread CPU time
- Lock contention (blocked time, lock class, waiting threads)
- Method profiling (sampled call tree)
- GC events, allocations

#### async-profiler — best open-source option
```bash
./asprof -d 30 -f profile.html <pid>
# Generates flame graph — visual CPU usage by call stack
```
Flame graph: width = CPU time. Find the widest bars = hottest code.

#### VisualVM / JConsole
- Free, ships with JDK
- CPU profiler: instruments methods or samples stacks
- Thread tab: real-time thread state visualization
- Sampler: lower overhead than instrumentation mode

#### Linux `perf` + `jstack`
```bash
# Find highest CPU thread (from OS perspective)
top -H -p <pid>     # shows per-thread CPU
# Convert to hex → match nid in thread dump
printf '%x\n' <tid>  # decimal TID → hex → find in jstack output
```

### Thread CPU profiling workflow (manual)

```bash
# 1. Find top CPU-consuming OS threads
top -H -p <pid>

# 2. Note the TID of the hot thread (decimal)
# e.g., TID = 12345

# 3. Convert to hex
printf '%x\n' 12345   # → 3039

# 4. Take thread dump and search for nid=0x3039
jstack <pid> | grep -A 30 "nid=0x3039"
# → shows exactly which Java method is consuming CPU
```

### Lock contention profiling with JFR

JFR captures `jdk.JavaMonitorWait` and `jdk.JavaMonitorEnter` events. In JMC, the "Lock Instances" view shows:
- Lock class
- Total wait time
- Number of blocked threads
- Stack trace at contention point

## Code

```java
import com.sun.management.ThreadMXBean;
import java.lang.management.*;

public class ThreadCpuProfiling {
    public static void main(String[] args) throws InterruptedException {
        com.sun.management.ThreadMXBean tmx =
            (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        tmx.setThreadCpuTimeEnabled(true);
        tmx.setThreadAllocatedMemoryEnabled(true);

        // Create some workload
        Thread worker = new Thread(() -> {
            long end = System.currentTimeMillis() + 2000;
            while (System.currentTimeMillis() < end) {
                Math.sqrt(Math.random()); // CPU work
            }
        }, "cpu-worker");
        worker.start();
        Thread.sleep(500);

        // Sample CPU time
        long[] ids = tmx.getAllThreadIds();
        for (long id : ids) {
            ThreadInfo info = tmx.getThreadInfo(id);
            if (info == null) continue;
            long cpuMs  = tmx.getThreadCpuTime(id) / 1_000_000;
            long userMs = tmx.getThreadUserTime(id) / 1_000_000;
            long allocKB = tmx.getThreadAllocatedBytes(id) / 1024;
            System.out.printf("%-40s cpu=%5dms user=%5dms alloc=%6dKB%n",
                info.getThreadName(), cpuMs, userMs, allocKB);
        }

        worker.join();
    }
}
```

## Interview Questions

**Q: What is a flame graph and how do you use it for thread profiling?**
> A flame graph shows call stacks on the X-axis (width = CPU time) and stack depth on the Y-axis. The widest bars are the hottest code paths. Generated by async-profiler or JFR; use to identify the exact method causing high CPU usage.

**Q: How do you find which Java thread is consuming high CPU on Linux?**
> `top -H -p <pid>` shows per-thread CPU. Note the TID, convert to hex with `printf '%x\n' <tid>`, then find `nid=0x<hex>` in a thread dump (`jstack <pid>`).

**Q: What is the overhead of JFR profiling?**
> Approximately 1–2%, making it safe for production. async-profiler with sampling is similarly low overhead. Instrumentation-based profiling (VisualVM full instrumentation mode) can be 10–100× higher.

## Cheat Sheet
| Tool | Overhead | Best for |
|---|---|---|
| JFR + JMC | ~1-2% | Production profiling, lock contention |
| async-profiler | ~1-2% | Flame graphs, CPU profiling |
| VisualVM | Medium–high | Dev/test interactive profiling |

| SpotBugs | Static | Finding potential issues before runtime |
